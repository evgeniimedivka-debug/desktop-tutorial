# NocoDB — изменения в таблице «Ролики»

База: «Контент-завод Milis Decor» (`pgcrh775xcev3n6`), таблица «Ролики»
(`mbv0dd92dx4irfp`).

## Новые поля

| Поле | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `Одобрено владельцем` | Checkbox | `false` | Единственный ключ запуска автопубликации. Проставляет владелец вручную в Gallery-view «Согласование» (см. ниже). Пока `false` — CF-08/CF-09 запись не трогают. |
| `Статус публикации` | Single select | `на согласовании` | Витрина состояния, см. значения ниже |
| `Дата одобрения` | DateTime | пусто | Проставляется автоматически в CF-08 в момент, когда webhook по чекбоксу первый раз сработал |
| `Дата публикации TG` | DateTime | пусто | Проставляется в CF-08 |
| `Дата публикации IG` | DateTime | пусто | Проставляется в CF-09 |
| `TG message id` | Text | пусто | id сообщения в канале — для аудита и ссылки |
| `IG media id` | Text | пусто | id опубликованного медиа в Instagram |
| `Ошибка публикации` | Long text | пусто | Текст последней ошибки, если публикация упала |

## Статусная модель `Статус публикации`

```
на согласовании → одобрено → опубликовано в Telegram → опубликовано в Instagram
                                                     ↘ ошибка публикации (ручной разбор)
```

- «на согласовании» — стартовое значение для новой единицы контента.
- «одобрено» — ставится CF-08 в момент старта обработки, сразу после
  того как владелец поставил `Одобрено владельцем=true` в Gallery-view.
- «опубликовано в Telegram» — ставится CF-08 после успешного `sendPhoto`/
  `sendVideo`. Это триггер для CF-09.
- «опубликовано в Instagram» — финальный статус, ставится CF-09.
- «ошибка публикации» — если Telegram/Instagram API вернул ошибку;
  запись не продвигается дальше автоматически, нужен ручной повтор
  (сбросить статус на предыдущий шаг после исправления причины).

## Защита от дублей

Перед действием каждый workflow (CF-08, CF-09) сверяет `Статус
публикации` записи — если он уже дальше по цепочке, чем ожидается на
входе в workflow, запись пропускается без повторной публикации. Это
страхует от повторного срабатывания webhook'а NocoDB (retry на сетевой
сбой и т.п.).

## Согласование — Gallery View «Согласование» (отдельная инфраструктура, без бота и без переписки)

Вместо команды боту или переписки в чате — отдельный вид в уже
работающей NocoDB, специально под ревью:

- Таблица «Ролики» → View → New View → **Gallery** → назвать
  «Согласование».
- Filter: `Статус публикации = на согласовании`.
- Cover image / video preview — поле с файлом (превью видео и фото
  прямо в карточке, без скачивания).
- В карточке видно: подпись, аватар (Даша/Евгений), дату, и чекбокс
  `Одобрено владельцем` — прямо там его и проставляет владелец.
- Опционально: Kanban-view с колонками по `Статус публикации` — для
  общей картины, что ещё ждёт согласования, что уже в очереди на
  публикацию.

Это полностью отделяет согласование от публикации: владелец работает
только в NocoDB UI, не пишет ни боту, ни в переписке с автоматизацией —
он не публикует ничего сам и не участвует в самом шаге отправки в
Telegram/Instagram.

## Webhook в NocoDB (Automation → Webhooks)

Один webhook на таблице «Ролики», условие — чекбокс сменился на `true`:

**On row update**, условие `Одобрено владельцем = true` (сработает один
раз, когда владелец ставит галочку в Gallery-view) →
`POST https://n8n.31-130-131-58.sslip.io/webhook/cf/publish-telegram`
(заголовок `x-cf-secret: <тот же секрет, что у /webhook/cf/render>`),
тело — вся строка (NocoDB делает это по умолчанию).

Второй шаг (публикация в Instagram) запускается отдельным webhook'ом:

**On row update**, условие `Статус публикации = опубликовано в Telegram` →
`POST https://n8n.31-130-131-58.sslip.io/webhook/cf/publish-instagram`
(тот же заголовок-секрет).

Настраивается в NocoDB UI: таблица «Ролики» → Details → Webhooks → New
Webhook → Event: After Update → Condition по полю → URL/headers как
выше.
